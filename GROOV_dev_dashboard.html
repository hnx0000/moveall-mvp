6. 최초 온보딩 사용 목적 조사
질문: GROOV를 어떻게 사용하고 싶으세요? 1. 내 운동을 기록하고 싶어요 → 순수 기록형 2. 기록을 공유하고 사람들과 소통하고 싶어요 → 기록 + SNS형 3. 다른 사람과 경쟁하며 운동하고 싶어요 → 경쟁형 4. 나만의 목표와 성취를 모으고 싶어요 → 개인 성취형 ‘지금 가장 큰 목적 하나’만 단일 선택한다. 기본 선택은 없고 건너뛰기가 가능하다. 복합 목적을 부정하는 분류가 아니라 가입 당시 주된 의도를 알아보는 한 문항이다. 운동 목표(체력·체중 등)와 사용 목적은 별도 값이다. - 기능 제한·자동 탭 재배치·개인 공개 프로필 표시를 하지 않는다. - 첫 온보딩 완료 때 응답 또는 명시적 건너뜀, 서버 시각, 질문 버전을 계정에 저장한다. - 재전송·설정 재저장으로 최초 응답을 중복 집계하거나 덮어쓰지 않는다. - 이전 가입자에게 값을 추정해서 채우거나 설문을 강제로 다시 띄우지 않는다. - 질문을 바꾸면 버전을 올리고 서로 다른 질문의 응답을 무분별하게 합치지 않는다. - 계정 삭제 시 응답도 삭제한다. 현재 집계는 조회 시점에 남아 있는 계정을 대상으로 하며 영구적인 가입 당시 스냅샷이 아니다. ### 구성비 해석 규칙 유형별 비율의 분모는 실제 응답자 수다. 집계 대상 가입자 수, 응답 수·응답률, 건너뜀, 미수집, 제외 계정 수, 가입 기간, 집계 시각을 함께 확인한다. 미수집 = 설문 도입 이전 가입자 또는 온보딩 미완료 등 아직 저장된 답변이 없는 계정. 건너뜀은 기록형이 아니다. 답변이 없으면 비율은 —로 표시한다. 운영자와 기본 데모 계정은 제외하고 미리보기 데이터는 실제 통계로 표시하지 않는다. 추가로 만든 테스트 계정은 출시 전 별도로 정리·분리해야 한다. 예시 기록 42% / SNS 31% / 성취 19% / 경쟁 8%는 설명용이지 현재 측정 결과가 아니다. 구성비는 투자 비중을 정하는 근거 중 하나다. 유형별 핵심 목적 달성·재사용·불만의 심각도·개발 비용과 함께 판단한다. 가입 의도를 실제 행동이나 만족도로 단정하지 않고, 소수 유형도 계속 검증한다.
7. 구현·확인 위치
- 온보딩: /onboarding, 사용 목적이 첫 단계. 기존 동네 인증 포함 흐름 유지. - 관리자: 내 정보 → 계정 → 사용 목적 통계 (/profile/product-insights). 전체/최근 30일 가입자를 조회한다. 서버 관리자 권한 필요. - 집계 API: GET /v1/admin/usage-purposes. registeredFrom 포함, registeredBefore 제외의 ISO 날짜시각 범위를 지원한다. 응답에는 개인 식별자를 넣지 않는다. - 데이터 마이그레이션: 0017_onboarding_usage_purpose.sql. 이번 로컬 작업에서 운영 DB 적용·공개 배포는 하지 않는다. - 이 문서는 제품 판단 기준의 원본이다. 출시 작업 체크 완료와 사용자 검증 완료를 합산하지 않는다. ### 구현 검사와 남은 검증 — 2026-09-03 - 로컬 자동 테스트 130개 통과: 공통 계약 25개, API 53개, 앱 로직 52개. 타입 검사·변경 코드 린트·웹 빌드 통과. - 신규 검사: 네 응답 값과 선택 건너뛰기, 최초 응답 보존·중복 집계 방지, 재조회, 가입 기간 경계, 관리자 접근 제한, 식별자 없는 집계, 탈퇴 후 집계 제외, 데모 응답 분리. - PostgreSQL 쿼리·매핑은 모의 DB 응답으로 검사했다. 운영 DB에 마이그레이션을 적용하거나 실제 DB 저장·재접속 검증을 완료한 상태는 아니다. 배포 시 0017 적용 → API → 앱 순으로 반영하고 실제 저장·조회·삭제를 확인한다. - 실제 사용자 대상 만족도 관찰과 휴대폰 온보딩 사용성 검증은 별도로 남아 있다. 위 자동 검사 결과로 1~4번 유형의 체크를 대신하지 않는다.

설계 원칙
GROOV 백엔드는 Fastify API → PostgreSQL 구조를 유지합니다. Supabase는 현재의 PostgreSQL 운영 제공자로 사용하고, 애플리케이션 코드가 Supabase 전용 SDK에 과도하게 종속되지 않도록 DB 접근은 기존 PostgresStore 계층을 중심으로 유지합니다. 향후 필요하면 Neon, AWS RDS 등 다른 PostgreSQL로 이전 가능하게 설계합니다.
인프라 확장 계획
개발 · Supabase Free (PostgreSQL)→ 출시 · Supabase Pro (동일 DB)→ 성장 · PostgreSQL 유지 + 미디어만 Cloudflare R2
R2는 DB 교체가 아니라 사진·영상용 Object Storage 확장입니다. 회원·운동·소셜 데이터는 PostgreSQL 계열에 유지하는 방향.

현재 기술 결정 · 확정
DB는 Supabase PostgreSQL로 진행합니다. 출시 초기에는 Supabase Pro로 전환하고, 사용자 증가 시 DB를 R2로 바꾸는 것이 아니라 사진·영상 Object Storage만 Cloudflare R2로 확장합니다. PostgreSQL 중심 구조는 유지해 향후 인프라 이전 여지를 남깁니다.
한 줄 결론
“프로토타입”은 이미 지났고, 지금은 “운영 가능한 베타”로 넘어가는 구간입니다.
언어를 새로 고르는 단계가 아니라, 현재 TypeScript + Expo/React Native + Fastify + PostgreSQL 구조를 살리면서 운영 인프라를 붙이는 단계입니다.
본 대시보드는 2026-09-02 저장소·Supabase·Google OAuth 점검 + 출시 전 인프라·법적 준비·스토어·Health Connect/HealthKit 전략을 통합한 최신 스냅샷입니다. 자동 갱신 대시보드로 확장하려면 GitHub Actions 또는 별도 상태 JSON 생성 파이프라인을 붙이는 방식이 적합합니다.
