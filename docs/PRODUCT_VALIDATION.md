# GROO V 핵심 사용자 검증 체크리스트

제품 전체를 평가하는 상위 기준 · v1 · 2026-09-03

> 서로 다른 유형의 사용자 모두가 각자의 목적에서 충분한 만족을 얻는가?

개발 작업 목록, 버그 수정 목록, 출시 심사 목록과 분리한다. 기능 구현 완료를 사용자 만족 검증 완료로 간주하지 않는다. 한 사람이 여러 목적을 가질 수 있으며 아래 유형은 고정된 신분이나 기능 권한이 아니다.

## 1. 항상 확인할 네 유형

| 유형           | 제품이 제공해야 할 가치                         | 핵심 검증 질문                                        | 현재 사용자 검증 상태     |
| -------------- | ----------------------------------------------- | ----------------------------------------------------- | ------------------------- |
| ① 순수 기록형  | 신뢰할 수 있는 기록·누적·회고                   | SNS를 전혀 하지 않아도 계속 쓸 가치가 있는가?         | 미검증 — 사용자 근거 필요 |
| ② 기록 + SNS형 | 기록을 표현하고 사람들과 반응을 주고받는 즐거움 | 기록 → 제작 → 공유 → 반응의 과정이 충분히 재미있는가? | 미검증 — 사용자 근거 필요 |
| ③ 경쟁형       | 납득할 수 있는 경쟁과 다음 목표                 | 랭킹·대결·챌린지가 충분한 자극을 주는가?              | 미검증 — 사용자 근거 필요 |
| ④ 개인 성취형  | 남과 무관하게 쌓이는 성장과 성취                | 메달·마일스톤·개인기록만으로도 성취감을 얻는가?       | 미검증 — 사용자 근거 필요 |

‘미검증’은 미구현이라는 뜻이 아니다. 아직 해당 유형의 실제 사용 결과를 이 문서에 남기지 않았다는 뜻이다.

## 2. 유형별 검증 시나리오

각 항목은 실제 사용자 관찰이나 피드백의 근거를 연결한 뒤 체크한다. 구현 코드나 테스트 통과만으로 체크하지 않는다.

### ① 순수 기록형 — SNS 없이 일주일 사용

- [ ] 팔로우·게시·댓글·사진 공개 없이 측정 또는 수동 입력 → 종료 → 저장을 완료한다.
- [ ] 측정치, 미측정치, 추정치, 수동 기록을 구분할 수 있고 재접속 후 기록이 유지된다.
- [ ] 원하는 날짜·종목의 기록을 다시 찾고 누적량과 지난 기록 대비 변화를 이해한다.
- [ ] 루틴 확인·완료와 회고에 SNS 참여나 공개 게시가 강제되지 않는다.
- [ ] 사용자가 “SNS를 하지 않아도 계속 사용할 이유”를 자기 말로 설명한다.

관찰: 저장 성공률·소요시간, 재조회 성공 여부, 회고 이해도, 일주일 후 기록 재사용 여부, 만족/불만 이유. 위치·센서 권한을 거절한 경우도 포함한다.

### ② 기록 + SNS형 — 기록 하나를 만들고 실제 상대와 반응

- [ ] 사진+기록, 사진+루트, 기록만, 글만 중 원하는 방식으로 타인 도움 없이 게시한다.
- [ ] 처음에는 그룹 편집만으로 충분하고 고급 레이어 편집은 원할 때만 사용한다.
- [ ] 공개·댓글 범위를 이해하고 원하는 사람에게 실제로 전달되는지 확인한다.
- [ ] 좋아요·댓글·대댓글·탭 공유와 알림이 이어져 상대의 반응을 확인한다.
- [ ] 반복되는 반응이 피로하거나 방해되지 않으며 다시 기록을 공유하고 싶다고 느낀다.

관찰: 기록 가져오기부터 게시까지의 성공률·시간·이탈 지점, 실제 상대와의 반응 왕복, 다음 공유 의향과 이유. 단순 좋아요 수를 만족도의 대체 지표로 쓰지 않는다.

### ③ 경쟁형 — 참여 → 순위 이해 → 다음 도전

- [ ] 자신의 종목·동네에 맞는 경쟁을 찾고 참가 조건과 인증·시즌 규칙을 이해한다.
- [ ] 순위 산정 근거, 상대와의 차이, 다음에 달성할 목표를 설명한다.
- [ ] 새 기록이 순위·챌린지에 어떻게 반영됐는지 확인한다.
- [ ] 부정확한 기록·조작 의심·동점·참여자 부족 상황을 납득할 수 있게 처리한다.
- [ ] 상위권이 아니어도 다음 도전을 원하고, 위험한 무리나 원치 않는 공개를 강요받지 않는다.

관찰: 규칙 이해도, 자발적 재참여, 목표 설정 이유, 공정성 체감, 하위권·입문자의 이탈 이유. 경쟁 UI 노출만으로 경쟁 경험을 충족했다고 보지 않는다.

### ④ 개인 성취형 — 타인 순위 없이 나의 성장 확인

- [ ] 다른 사람과 비교하지 않고 개인 목표를 설정하고 진행 상황을 이해한다.
- [ ] 개인기록 경신·누적 운동·루틴 지속 등 자신의 변화가 성취로 연결된다.
- [ ] 메달·마일스톤의 획득 조건과 달성 근거를 확인한다.
- [ ] 혼자 운동하거나 기록을 비공개로 유지해도 개인 성취가 인정되고 다시 조회된다.
- [ ] 작은 성장도 의미 있게 느끼며 실패·휴식 뒤에도 다시 시작할 수 있다고 느낀다.

관찰: 목표/보상 의미 이해도, 달성 후 만족 이유, 다음 개인 목표, 비공개 이용자의 재방문 의향. 경쟁 순위나 타인의 반응이 없어도 검증한다.

## 3. 모든 유형의 공통 통과 조건

- [ ] 사용 목적 선택·건너뛰기에 따라 탭, 기능, 권한, 요금, 접근 경로를 분리하지 않는다.
- [ ] 개인정보·공개 범위·삭제 선택이 예상대로 작동한다. 원치 않는 SNS 게시를 만들지 않는다.
- [ ] 주요 기록 유실·중복·잘못된 측정값·다른 사용자 노출 같은 중대한 오류가 없다.
- [ ] 작은 화면·큰 글씨·느린 연결·권한 거절에서도 핵심 경로와 복구 방법을 찾는다.
- [ ] 한 유형의 개선이 다른 유형의 필수 경로를 복잡하게 하거나 가리지 않는다.

공통 조건의 심각한 실패는 전체 평균 만족도로 상쇄하지 않는다. 특정 유형의 사용자 비중이 작아도 그 유형의 기본 사용 가치를 없애지 않는다.

## 4. 검증 운영과 기록 양식

새 핵심 기능 추가 전/후, 핵심 동선 변경 후, 베타·출시 판단 전에 같은 기준으로 재검증한다. 그 외 수정은 관련 시나리오와 네 유형에 대한 회귀 영향을 확인한다. 다음 라운드가 시작되면 이전 체크를 자동 승계하지 말고 새 기록을 남긴다.

상태: **미검증 / 검증됨 / 개선 필요 / 보류(사유 필수)**. 검증 담당자가 상태를 정하고 근거를 연결한다. 목표 성공률·시간·만족도 기준은 결과를 보기 전에 라운드별로 정한다. 적은 표본은 탐색 결과로만 보고 대표성을 주장하지 않는다.

```text
라운드 / 일자 / 담당자 / 앱 버전:
검증 대상 유형 / 참여자 수 / 모집 방법:
사용 환경: 기기, OS, 네트워크, 권한 상태
검증 전 가설과 성공 기준:
시나리오 / 도움 없이 성공한 수 ÷ 시도 수 / 소요시간:
목적 달성 만족도(1~5)와 사용자의 이유:
재사용 의향과 실제 재사용 여부(관찰하지 못했다면 미확인):
막힌 지점 / 오류 / 예상과 다른 행동:
근거 링크: 익명화한 관찰 기록·인터뷰·이슈
판정 / 개선할 항목 / 담당자 / 재검증 시점:
다른 세 유형에 대한 영향:
```

원본 위치·건강 기록·계정 식별자 대신 익명 참여자 코드를 사용한다. 아직 실시하지 않은 사용자 검증을 성공 수치로 채우지 않는다.

## 5. 신규 기능 역체크 — 개발 시작·리뷰 시 필수

| 확인할 것                     | 작성 내용                                          |
| ----------------------------- | -------------------------------------------------- |
| 누구를 위한 기능인가?         | 네 유형 중 주 수혜 유형과 부수 수혜 유형           |
| 어떤 목적을 더 잘 달성하는가? | 기존 불편 → 변화 → 사용자 가치 한 문장             |
| 실제 필요의 근거는?           | 유형 구성비, 관찰/인터뷰, 이탈·오류 등의 근거 링크 |
| 좋아졌다고 어떻게 판단하는가? | 관련 시나리오와 검증 전 성공 기준                  |
| 다른 유형에 손해는 없는가?    | 기록 전용·비공개·비경쟁 사용 경로의 회귀 확인      |
| 도입·보류·축소 판단은?        | 결과, 남은 불확실성, 담당자, 재검증 시점           |

이 항목은 PR 양식에도 반영한다. 순수 유지보수는 직접 수혜가 없는 이유를 적고 회귀 영향을 확인한다.

## 6. 최초 온보딩 사용 목적 조사

질문: **GROOV를 어떻게 사용하고 싶으세요?**

1. 내 운동을 기록하고 싶어요 → 순수 기록형
2. 기록을 공유하고 사람들과 소통하고 싶어요 → 기록 + SNS형
3. 다른 사람과 경쟁하며 운동하고 싶어요 → 경쟁형
4. 나만의 목표와 성취를 모으고 싶어요 → 개인 성취형

‘지금 가장 큰 목적 하나’만 단일 선택한다. 기본 선택은 없고 건너뛰기가 가능하다. 복합 목적을 부정하는 분류가 아니라 가입 당시 주된 의도를 알아보는 한 문항이다. 운동 목표(체력·체중 등)와 사용 목적은 별도 값이다.

- 기능 제한·자동 탭 재배치·개인 공개 프로필 표시를 하지 않는다.
- 첫 온보딩 완료 때 응답 또는 명시적 건너뜀, 서버 시각, 질문 버전을 계정에 저장한다.
- 재전송·설정 재저장으로 최초 응답을 중복 집계하거나 덮어쓰지 않는다.
- 이전 가입자에게 값을 추정해서 채우거나 설문을 강제로 다시 띄우지 않는다.
- 질문을 바꾸면 버전을 올리고 서로 다른 질문의 응답을 무분별하게 합치지 않는다.
- 계정 삭제 시 응답도 삭제한다. 현재 집계는 조회 시점에 남아 있는 계정을 대상으로 하며 영구적인 가입 당시 스냅샷이 아니다.

### 구성비 해석 규칙

유형별 비율의 분모는 **실제 응답자 수**다. 집계 대상 가입자 수, 응답 수·응답률, 건너뜀, 미수집, 제외 계정 수, 가입 기간, 집계 시각을 함께 확인한다.

미수집 = 설문 도입 이전 가입자 또는 온보딩 미완료 등 아직 저장된 답변이 없는 계정. 건너뜀은 기록형이 아니다. 답변이 없으면 비율은 `—`로 표시한다. 운영자와 기본 데모 계정은 제외하고 미리보기 데이터는 실제 통계로 표시하지 않는다. 추가로 만든 테스트 계정은 출시 전 별도로 정리·분리해야 한다.

예시 **기록 42% / SNS 31% / 성취 19% / 경쟁 8%**는 설명용이지 현재 측정 결과가 아니다.

구성비는 투자 비중을 정하는 근거 중 하나다. 유형별 핵심 목적 달성·재사용·불만의 심각도·개발 비용과 함께 판단한다. 가입 의도를 실제 행동이나 만족도로 단정하지 않고, 소수 유형도 계속 검증한다.

## 7. 구현·확인 위치

- 온보딩: `/onboarding`, 사용 목적이 첫 단계. 기존 동네 인증 포함 흐름 유지.
- 관리자: 내 정보 → 계정 → 사용 목적 통계 (`/profile/product-insights`). 전체/최근 30일 가입자를 조회한다. 서버 관리자 권한 필요.
- 집계 API: `GET /v1/admin/usage-purposes`. `registeredFrom` 포함, `registeredBefore` 제외의 ISO 날짜시각 범위를 지원한다. 응답에는 개인 식별자를 넣지 않는다.
- 데이터 마이그레이션: `0017_onboarding_usage_purpose.sql`. 이번 로컬 작업에서 운영 DB 적용·공개 배포는 하지 않는다.
- 이 문서는 제품 판단 기준의 원본이다. 출시 작업 체크 완료와 사용자 검증 완료를 합산하지 않는다.

### 구현 검사와 남은 검증 — 2026-09-03

- 로컬 자동 테스트 130개 통과: 공통 계약 25개, API 53개, 앱 로직 52개. 타입 검사·변경 코드 린트·웹 빌드 통과.
- 신규 검사: 네 응답 값과 선택 건너뛰기, 최초 응답 보존·중복 집계 방지, 재조회, 가입 기간 경계, 관리자 접근 제한, 식별자 없는 집계, 탈퇴 후 집계 제외, 데모 응답 분리.
- PostgreSQL 쿼리·매핑은 모의 DB 응답으로 검사했다. 운영 DB에 마이그레이션을 적용하거나 실제 DB 저장·재접속 검증을 완료한 상태는 아니다. 배포 시 `0017` 적용 → API → 앱 순으로 반영하고 실제 저장·조회·삭제를 확인한다.
- 실제 사용자 대상 만족도 관찰과 휴대폰 온보딩 사용성 검증은 별도로 남아 있다. 위 자동 검사 결과로 1~4번 유형의 체크를 대신하지 않는다.
